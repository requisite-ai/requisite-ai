
# 0014. `requisite` CLI: scaffolding, registry introspection, and quick chat

Status: Accepted
Date: 2026-08-11

## Context

`ROADMAP.md`'s one remaining `## CLI` line names the feature exactly:
*"scaffold a project, list registered providers/capabilities/agents, run a
quick chat."* Unlike the multi-agent strategies shipped earlier this
stretch, this isn't an incremental library capability -- it's the one
remaining item that changes *onboarding* (`pip install` to a running
agent) rather than adding to what an already-onboarded application can do.

Everything today is Python-API-only: no `[project.scripts]` entry, no CLI
framework dependency, no `cli.py`/`__main__.py` anywhere in the repo
(confirmed by grep). Three of the four requested capabilities map directly
onto existing registries: `ProviderRegistry.available()`,
`CapabilityRegistry.list_capabilities()`/`.providers_for()`, and
`AI`/`Agent` for chat. The fourth -- "list registered agents" -- has no
existing target. `AgentRegistry` exists (`requisite/agents/registry.py`)
but, unlike every other registry in the framework, ships with **no
`default_registry` instance**. There's no such thing as a "built-in
agent" the way there's a built-in OpenAI provider or a built-in `weather`
capability -- every `Agent` is user-constructed. Resolving that gap, and
choosing a CLI framework consistent with the project's dependency policy,
are the two decisions this ADR records.

## Decision

### `argparse`, not `click`/`typer` -- no new dependency

`DEVELOPMENT.md`'s dependency policy is explicit: *"Think twice before
adding a new hard dependency... prefer the standard library where
reasonable."* The command surface here is five subcommands with plain
flags (`init`, `providers`, `capabilities`, `agents`, `chat`) -- it doesn't
need `click`'s decorators or `typer`'s type-driven parsing enough to
justify a dependency every `pip install requisite-ai` user would pull in,
even those who never touch the CLI. `argparse` (stdlib) is used directly
in `requisite/cli/main.py`.

### The "list agents" gap: a project convention (`agents.py` + `agent_registry`), not a new global registry

`requisite init NAME` scaffolds an `agents.py` with a module-level
`agent_registry: AgentRegistry` variable
(`requisite/cli/scaffold.py::_agents_py`). `requisite agents` and
`requisite chat --agent NAME` both import that file from the current
directory (`requisite/cli/project.py::load_agent_registry`, via
`importlib.util.spec_from_file_location`) and read `agent_registry` off
the loaded module. No `agents.py`, or no `agent_registry` attribute of the
right type, produces a `ConfigurationException` pointing at `requisite
init` rather than a traceback.

This mirrors Flask's `app.py` / Django's `manage.py` discovery pattern:
the CLI needs *some* well-known place to look, and a scaffolded project is
exactly where that convention gets established. It also keeps the
"no global mutable state" precedent every other registry in the framework
follows (`ARCHITECTURE.md`) -- each scaffolded project gets its own
`AgentRegistry` instance; there is still no framework-wide agent registry
singleton anywhere.

### Package layout

```
requisite/cli/
├── __init__.py    # exports `main`
├── main.py        # argparse parser + dispatch + error boundary
├── commands.py     # cmd_init, cmd_providers, cmd_capabilities, cmd_agents, cmd_chat
├── scaffold.py     # init's file templates
└── project.py      # load_agent_registry (shared by `agents` and `chat --agent`)
requisite/__main__.py   # `python -m requisite`
```

`main(argv=None, *, registry=None, settings=None)` accepts an injectable
`ProviderRegistry`/`Settings`, the same DI shape `AI.__init__` already
uses -- specifically so `tests/test_cli.py` can register a fake provider
and settings without touching the shared `default_registry` or reading
the repo's real `.env`.

`pyproject.toml` gains `[project.scripts] requisite =
"requisite.cli.main:main"` -- the first entry point this repo has ever
had. `requisite/__main__.py` gives the equivalent `python -m requisite`
path with no extra logic of its own.

### `print()` is a deliberate, scoped exception to "never `print()`"

`DEVELOPMENT.md`: *"Never use `print()`. Use the standard library `logging`
module."* That rule targets library code emitting diagnostic/debug
information to whoever configures logging. A CLI's stdout is not a log --
it *is* the product being delivered to a terminal user, and framework
conventions elsewhere (structured logging is opt-in, never automatic --
ADR-0003) already assume application code, not the framework, owns
user-facing output. `requisite/cli/commands.py` uses `print()`
throughout; internal framework code (everything outside `requisite/cli/`)
is unaffected and still never prints. This is the same treatment
ADR-0002 gave the `OpenAIProvider`-subclassing exception to "composition
over inheritance": named, scoped, and justified rather than silently
inconsistent.

### `requisite providers` reports SDK-installed and API-key-configured status

Beyond `ProviderRegistry.available()` (just names), `cmd_providers` checks
`importlib.util.find_spec(...)` against a small provider-to-SDK-module map
and `Settings.api_key_for(name)`, so a new user immediately sees which
providers are ready to use versus which need `pip install
requisite-ai[x]` or a `.env` key -- the concrete onboarding gap this
feature exists to close.

### `requisite capabilities` never triggers a network call

`CapabilityProvider.is_available()` is checked (not `.execute()`), and the
three built-in capabilities' `is_available` all default to
`_always_available` (`requisite/capabilities/resolvers.py`) -- listing
capabilities is always a pure registry read, matching
`DEVELOPMENT.md`'s "no test may require network access" constraint for
`tests/test_cli.py` as well as real-world CLI use (no surprise outbound
requests just from `requisite capabilities`).

## Alternatives considered

- **`click` or `typer`.** Rejected on the dependency policy above --
  five straightforward subcommands don't earn a new always-installed
  dependency. Revisit if the CLI's surface grows enough (nested
  subcommand groups, shell completion) that `argparse`'s boilerplate
  becomes the bigger cost.
- **A framework-wide default `AgentRegistry`, analogous to
  `default_registry`/`default_capability_registry`.** Rejected: there is
  no meaningful "built-in agent" to pre-populate it with (contrast
  built-in providers/capabilities, which are real, useful defaults), and
  adding an always-shared mutable `AgentRegistry` specifically to serve
  the CLI would be the first crack in the "no global mutable state, no
  singletons" precedent (`DEVELOPMENT.md`) purely for the CLI's
  convenience -- worse than establishing a per-project file convention.
- **Entry-point plugin discovery (`requisite-plugin-*`) feeding
  `requisite providers`/`requisite capabilities`.** Explicitly out of
  scope here -- it's already its own roadmap item (`ROADMAP.md`'s
  "Plugin architecture" section) and a natural, separate follow-up once
  it ships; bundling it into this ADR would conflate "list what's
  registered right now" with "discover what could be installed."
- **`requisite chat --agent` reading provider/model overrides from CLI
  flags even when `--agent` is set.** Rejected for v1: the scaffolded
  agent's provider is fixed by how `agents.py` constructs it, and
  layering a second configuration path on top (CLI flags silently
  overriding a user-edited `agents.py`) adds surprise for no clear
  onboarding benefit. `--provider`/`--model` are simply ignored when
  `--agent` is given.

## Consequences

### Positive

- Closes the last `📋` line in `ROADMAP.md`'s CLI section end to end:
  `requisite init` gets a new user from nothing to a running agent in
  four commands (`pip install`, `cp .env.example .env`, fill a key,
  `python main.py` or `requisite chat --agent assistant`).
- Zero new dependencies for any existing `pip install requisite-ai` user.
- `agent_registry` is a genuinely reusable convention beyond the CLI
  itself -- any script can define one and get `requisite agents`/`chat
  --agent` for free, not just scaffolded projects.

### Negative / risks

- **The `agents.py` convention is invented for this feature, not derived
  from anything already in the framework.** If application structure
  diverges (agents defined across multiple files, built dynamically at
  runtime), `requisite agents`/`chat --agent` won't see them unless the
  user still exposes one `agent_registry` variable somewhere and points
  `--module` at it. This is a real, accepted limitation of a
  single-file-convention approach, not a bug.
- **`requisite chat --agent`'s provider is fixed at scaffold time.** No
  way to swap providers for a quick chat through an agent without editing
  `agents.py` directly (see Alternatives above).
- `cmd_providers`' SDK-installed check
  (`_PROVIDER_SDK_MODULES` in `requisite/cli/commands.py`) is a
  hand-maintained map, separate from `ProviderRegistry`'s own lazy-import
  builders -- a new provider added to the registry needs a matching entry
  here too, or `requisite providers` silently reports "no" for SDK
  status. No test currently enforces this mapping stays in sync.

### Follow-ups

- If/when entry-point plugin discovery (`requisite-plugin-*`) ships, it's
  the natural place to widen `requisite providers`/`requisite
  capabilities` beyond "what's registered in the current process" to
  "what's installed and discoverable" -- see the rejected-alternative
  note above.
- `requisite chat --agent`'s single-provider-per-agent limitation could
  be revisited if a real use case for per-invocation provider overrides
  shows up; not scoped here since none has yet.
- The `_PROVIDER_SDK_MODULES` hand-maintained map (see risks) could move
  onto `BaseProvider` itself as a class attribute if it drifts out of
  sync in practice -- not done now since only one place currently needs
  it.
